# 新版客户端功能需求讨论

日期：2026-10-04。技术方向为 Avalonia，视觉基线为 Material 3 Expressive。

本文将用户明确的行为与用于讨论的候选方案分别记录。候选方案随后续回答收敛。

## 1. 下载管理

用户要求：加强下载管理。

候选基础能力：持久化队列；按作品归组、按文件展示进度；暂停、继续、取消、重试；批量操作；并发限制；断点恢复；后台及重启恢复；文件命名和目录配置；重复下载处理；完成后定位或分享文件。

需要用户确定：第一版最重要的下载场景与能力；插画、多图、动图和小说的交付格式。具体格式在相关作品类型的范围确定后继续展开。

上游事实：已有持久化记录、Range 续传、进度、通知取消与重试；同批文件被串成 WorkManager 依赖链。新版队列设计需要考虑单项失败后的其他任务推进。具体证据汇总在 `analysis/legacy-feature-flows.md`。

## 2. 收藏中间态

用户要求：点击收藏后呈现可感知的处理中状态，随后根据请求结果显示最终状态。

状态表达：当前稳定状态 → 收藏处理中 → 确认后的稳定状态。请求失败后保持可重试的明确反馈，并恢复上一次稳定状态；取消收藏采用对应的处理中状态。

候选交互：保留原图标轮廓或填充语义，在其周围或旁侧显示进度；同作品在列表和详情页共享处理中与最终状态。

需要用户确定：处理中再次点击时采用哪种意图处理方式。

上游事实：列表点击后直接修改图标状态；详情页面通过完成后的数据结果回显。两种现有反馈路径与用户描述对应。候选新方案将两处共享收藏状态，包括处理中。

## 3. 搜索词与历史管理

用户要求：沿用多关键词模糊搜索；增加可管理的搜索历史；点击历史记录时，将它加入当前搜索，搜索由用户显式提交。

候选交互：当前关键词以独立条目呈现，支持增加、删除、编辑；历史提供删除、清空和固定常用项；历史内容加入后保持编辑状态；实际提交后记录搜索历史。

已确定：搜索历史按单个词条管理，一次提交多个词条时，分别记录每个词条。例如提交 `猫耳 白发` 后，历史中分别出现 `猫耳` 与 `白发`。点击历史词条时，将该词条加入当前搜索并保持编辑状态。

候选管理规则：按最近使用时间排序，同一词条再次使用时更新位置和使用次数；用户可以删除、清空或固定词条；加入当前搜索时处理重复词条。

上游事实：搜索框按空格划分词条，对末词提供补全；搜索目标支持 PARTIAL_MATCH。历史需要建立相应持久化记录。

## 4. 中文呈现

用户要求：补充 tag 等页面的中文翻译。

已确定：标签中文复用已有项目的翻译能力或数据；页面文案由本项目自行编写和维护中文资源。

候选呈现：标签原名与中文译名共同展示，标签跳转与搜索使用对应的作品标签语义。现有项目来源及译名数据的接入方式在后续实现方案中选定。

上游事实：标签模型包含 `translated_name`，请求拦截器能够设置 `zh-hans` / `zh-hant`。搜索候选和趋势页面部分使用译名，作品详情标签仅绑定原名。新版统一各页面的标签呈现策略。

现有项目接入参考：Shaft 的 `V3TagFlowView.kt` 从 Pixiv 的 `translated_name` 字段建立标签译名，并复用历史保存的译名；其 `PixivWebApi.kt` 为相应接口传入中文语言。按这条已采用的译名数据路径设计独立标签呈现层，页面中文文案由本项目维护。[Shaft 标签实现](https://github.com/CeuiLiSA/Pixiv-Shaft/blob/b88b9008f440b22e34e80161380919b2feca6de3/app/src/main/java/ceui/pixiv/widgets/V3TagFlowView.kt)。具体项目或词库可随用户偏好替换。

## 5. Token 刷新与请求恢复

用户反馈：旧版似乎先刷新过期 Token，之后由手动刷新恢复请求。

目标行为：鉴权过期后刷新 Token，成功后自动恢复导致刷新发生的请求；同时发生的鉴权过期请求共享一次刷新，随后恢复各自流程。页面保留正在浏览的内容和位置，并连续呈现加载状态。

实现设计检查点：鉴权失败与普通网络错误的区分；刷新请求的单次并发协调；原请求内容的重建；账号切换与任务取消；收藏写操作的状态确认。具体策略在旧版流程证据和 API 行为核对后确定。

上游因果线索：插画/小说列表遇到鉴权错误后刷新 Token，新 Token 更新在同一个 Action 对象上；页面再次调用 ViewModel.show 时，相等判断会提前结束流程。新版通过鉴权层协调刷新与原请求恢复，同时用独立的请求状态驱动页面。

## 6. 双轴作品详情与常驻信息抽屉

用户要求：作品详情同时支持左右滑动与上下滑动；下方信息改为常驻抽屉，以适配上下滑动；参考 Shaft 的逻辑。

已确定：底部信息抽屉常驻作品标题、作者等信息。收藏入口采用独立悬浮按钮，延续旧版的独立按钮关系。

用户描述的旧版行为：在图片区横向切当前作品图片，到第一张或最后一张边界后继续切换相邻作品；在下方信息区横向操作时直接切换作品。用户希望融合 Shaft 的纵向图片浏览，并增加设置项切换图片区的滑动行为。

候选模式：横向分页模式沿用旧版图片区行为；纵向浏览模式采用 Shaft 式的当前作品多图纵向浏览。信息区保留横向直接切作品。纵向模式中的作品切换方式、图片边界手势和缩放优先级继续确认。

Shaft 参考事实：`classic` 分支提交 `b88b9008f440b22e34e80161380919b2feca6de3` 的经典详情页采用外层横向切作品、内部纵向滚动同作品多图。底部信息保留标题与作者栏的常驻高度，允许向上拉高；最大高度取内容高度与屏高 3/4 的较小值。新版手机 V3 与平板 V3 具有各自的结构。具体证据与版本差异记录在 `analysis/shaft-detail-reference.md`。

## 7. 悬浮收藏按钮与重力换边

用户要求：收藏按钮作为独立悬浮入口，增加重力感应，通过设备倾斜在屏幕左右两侧切换，方便单手操作。

已确定：重力控制的对象是按钮位置；收藏状态继续由点击操作与请求结果确定。左右两侧保持可触达的位置，换边后仍指向当前作品的同一收藏状态。

候选交互：设备向一侧倾斜并保持后，按钮吸附到该侧；回正后保留换边结果；明显的反向倾斜触发下一次换边。换边采用沿屏幕下侧的过渡，保证内容和按钮的触达关系。

候选参数：重力换边提供独立开关、灵敏度和校准；初始实验参数为约 25° 倾斜、保持约 400ms，结合平滑、回正阈值与切换间隔调节手感。这些数值属于真机调试起点。

平台事实：Android 的 TYPE_GRAVITY 提供重力方向与强度向量，可用于判断倾斜；界面方向变化后应按当前屏幕坐标解释侧向倾斜。参考 [Motion sensors](https://developer.android.com/develop/sensors-and-location/sensors/sensors_motion)。

候选手势协调：手指按住按钮、图片缩放或抽屉拖动时保持当前按钮位置，松手后继续判断换边；界面旋转后使用屏幕坐标重新解释倾斜方向；应用进入后台时结束本页的传感器监听。

需要用户确定：倾斜方向与按钮目标侧的对应关系、触发后的持续移动方式，以及功能的初始启用状态。

## 后续分支

评论与小说的兼容性修复保留为基础目标。下载格式、中文来源、账号与本地记录范围、控件库完整覆盖和平台交付范围，根据上述决策逐层展开。

## 当前讨论前沿

1. 下载管理中，队列恢复、批量作品操作、文件组织的优先级。
2. 收藏处理中再次点击时，保持本次操作还是记录用户最后一次意图。
3. 纵向图片模式中的相邻作品切换规则。
4. 重力换边的方向对应、触发形式及初始启用状态。
5. 抽屉展开内容与高度、搜索历史管理细节，以及标签中文接入来源，随相应核心规则确定后继续收敛。

GPU 调查支持继续当前 Avalonia 技术方向。功能与主题库的首轮性能场景见 `docs/stack-comparison.md` 的 Android GPU 加速补充。

## 正式界面设计约束

用户认可当前草图的大致交互方向。正式产品将图片区模式、重力开关和灵敏度配置归入设置或次级菜单；详情页围绕图片、常驻信息与独立悬浮收藏进行完整视觉设计。具体要求与验收状态见 `docs/ui-design-requirements.md`。
